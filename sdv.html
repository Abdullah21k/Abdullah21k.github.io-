Software-Defined
Vehicle Simulation.

A software-based vehicle network exploring how electronic control units exchange CAN-style messages, respond to driver inputs, and surface simulated faults.

01 · Overview

One vehicle. Multiple controllers.

The project models several vehicle subsystems as separate software programs: battery management, vehicle control, body control, motor/inverter, braking, driver input, and infotainment. Instead of physical CAN hardware, the programs exchange DBC-defined CAN-style data over a shared UDP multicast channel.

Communication

ECUs share messages on one simulated bus. Each module processes relevant messages using identifiers and a defined signal map.

02 · System design

How the ECUs communicate

Each simulated controller broadcasts messages to the same shared channel. Receivers filter by message ID, and the DBC mapping defines how signal values are represented in frame data.

Conceptual architecture based on project documentation. This is a software simulation, not a physical CAN hardware network.

03 · Example interaction

From driver input to dashboard

  1. Driver input: The driver selects Drive or presses the accelerator.
  2. Message broadcast: The driver input module publishes a CAN-style frame to the simulated shared bus.
  3. Vehicle response: The VCU processes relevant messages and updates the simulated vehicle state and speed.
  4. Display and monitoring: Infotainment shows vehicle status while the monitor exposes raw message traffic.

This sequence summarizes the documented simulation behavior; it is not a measured performance benchmark.

05 · Engineering takeaways

What this project demonstrates

The project illustrates ECU modularity, message-ID filtering, signal mapping, driver-to-controller interactions, and the role of monitoring and fault injection in vehicle software development. Its simulated network captures key communication concepts but does not reproduce physical CAN bus timing, arbitration, or error behavior.
